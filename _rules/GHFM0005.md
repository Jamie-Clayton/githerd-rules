# GHFM0005: yaml-alias

An '&anchor' or '*alias' token was found in the front-matter block. Aliases expand silently at parse time, so the document a human reads and the document a tool loads can differ, and deeply nested aliases are a denial-of-service vector on some parsers. Front-matter is a flat metadata contract; write the value out in full.

<!-- begin hand-authored content -->

## Trigger

A YAML anchor (`&name`) or alias (`*name`) token appears inside the front-matter
block. The check is a pre-parse text scan, so it fires whether or not the
parser would have expanded the alias successfully.

## Why the rule exists

Two reasons, and the second is the one that made this an `error`.

The readability reason: an alias expands silently at load time, so the document
a human reads and the document a tool loads are not the same document. Front
matter is a flat metadata contract that other people copy from; an anchor turns
it into a small program.

The safety reason: nested alias expansion is a denial-of-service vector. A
handful of anchors, each referring to the previous one, expands to a structure
large enough to exhaust memory. The mitigation options at parser level are
unreliable here, and a parser option that silently does nothing is worse than
no option, so the harness refuses the construct outright rather than trying to
bound it.

## Fix

1. Delete the anchor and write the value out in full at each place it is used.
2. If the repetition is genuinely painful, that is a signal the data belongs in
   a register under `docs/registers/` rather than in front matter.
3. Re-run the validator over the file. There is no suppression for this rule.
