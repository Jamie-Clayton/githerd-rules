A shoulder is the class discriminator embedded in every ARK document identifier: 'bs8' for initiative briefings, 'dr8' for decision records, 'sk8' for specs, and so on per the shoulder registry. ## About shoulders

A shoulder is the short class discriminator embedded in every document
identifier this repository mints: in `ark:/99999/dr86gcfrp60wrcdmj` the
shoulder is `dr8`, and it says the document is a decision record. The harness
does not read your front matter to work out which shoulder a document should
carry; it reads the document's **folder**, because the folder is what the rest
of the tooling already trusts. So when this rule says your file expects
shoulder `X`, the reason is always the same one: `X` is the shoulder registered
for the directory the file is sitting in, and the identifier in the file
carries a different one.

That is the whole mechanism, and the table below is the whole registry. Two
things follow from it. Moving a file between folders changes the shoulder it is
expected to carry, and copying an identifier from another document is the
fastest way to trip this rule, because you inherit that document's class along
with its blade.

## Shoulder registry

Eleven shoulders are registered. Source of truth is the shoulder-registry
decision record, [adr-030](https://github.com/Jamie-Clayton/githerd/blob/main/docs/architecture/ADRs/2026-04-23-adr-030-shoulder-registry-expansion-and-levity.md)
(repository access required), mirrored in `typespec/identity.tsp`. The
rightmost column is the validator's own path dispatch, and it is the column
that answers "why does my file expect this shoulder".

| Shoulder | Document class | Hub | Applies to paths |
| -------- | -------------- | --- | ---------------- |
| `bs8` | Initiative briefing | Explorer | `docs/initiatives/` |
| `sk8` | Design spec | Designer | `docs/specs/` |
| `dr8` | Decision record (ADR) | Designer | `docs/architecture/ADRs/` |
| `pt8` | Delivery plan | Delivery | `docs/plans/`, and any other `plans/` folder |
| `tk8` | Work item (story, bug, feature) | Delivery | `docs/workitems/` |
| `vt8` | UAT artifact | Delivery | `docs/uat/` |
| `nm8` | Metrics, trend, ROI | Measurement | not path-dispatched; no shoulder is asserted |
| `st8` | Status report, storytell, blog | Narrative | `docs/comms/`, `docs/reports/` |
| `dm8` | Idea, backlog | pre-Explorer | `docs/ideas/` |
| `dst8` | Daily note, archive snapshot | cross-cutting | `docs/archive/` |
| `gh8` | General, fallback | none | not path-dispatched; no shoulder is asserted |

Reading the table:

- **Hub** is the Autopilot hub that produces that document class. It is in the
  table because it explains the grouping: three Delivery shoulders exist
  because Delivery emits three genuinely different artefacts, not because the
  registry is fussy.
- **Applies to paths** is matched in the order shown, first match wins. A file
  under `docs/plans/` matches the plan row before it reaches the general
  `plans/` row, and both resolve to `pt8` anyway.
- Two shoulders are **not path-dispatched**. `nm8` and `gh8` have no folder
  mapping, so this rule never asserts a shoulder for a file outside the mapped
  directories and never fires there. A general document carrying `gh8` is
  correct by construction.
- `dst8` is the only three-consonant shoulder. If a tool of yours assumes two
  consonants and a digit, it will mismatch `dst8` silently; the pattern is two
  to four betanumeric consonants followed by a digit.

**Retired shoulders, do not reuse.** `nd8`, `wk8`, `sp8` and `pk8` appear in
old git history and in archived documents. They are retired rather than
recycled precisely so that excavating one from history is unambiguous. `sp8`
became `sk8`, `pk8` became `pt8`, and `wk8` split into `bs8` and `tk8`.

## Trigger

The document declares an `identifier`, the identifier parses as an ARK, and the
shoulder it carries is not the shoulder registered for the file's directory.
The rule is silent when the document has no `identifier` and when the file sits
outside every mapped directory.

## Why the rule exists

An identifier is meant to outlive the repository that minted it, so its class
discriminator has to be right on the day it is minted; there is no correcting
it later without a forward-alias operation and a superseding decision record.
Two ordinary editing actions break the invariant. A file moved between folders
keeps the identifier it was minted with, which is now the wrong class. An
identifier copied from a nearby document as a starting point brings that
document's class with it, and frequently its blade too, which quietly creates
two documents claiming the same identity.

## Fix

1. Decide which is wrong, the folder or the identifier. Ask what the document
   **is**, not where it currently sits.
2. If the folder is wrong, `git mv` the file to the directory its class maps to
   in the table above. The identifier is then already correct.
3. If the identifier is wrong, remint it for the correct shoulder rather than
   hand-editing the three shoulder characters. A hand-edited identifier keeps a
   blade that was minted under another shoulder, and blades are unique per
   shoulder, not globally.
4. Never resolve this by copying an identifier from a sibling document. Two
   documents with one identifier is a worse defect than the one you started
   with, and no rule on this site detects it.

**Quotable fix.** Paste this into a review comment:

> **GHFM0008 (identifier-shoulder-mismatch).** The shoulder in this
> document's ARK identifier does not match the shoulder registered for its
> folder. A shoulder is the document-class discriminator inside the
> identifier, and the expected value comes from the file's directory:
> `docs/specs/` expects `sk8`, `docs/architecture/ADRs/` expects `dr8`,
> `docs/plans/` expects `pt8`, `docs/initiatives/` expects `bs8`. Either move
> the file to the folder that matches its class, or remint the identifier for
> the correct shoulder. Do not hand-edit the shoulder characters and do not
> copy an identifier from another document.

## Enforcement

Default severity is `warning` today, so the finding annotates a pull request
without blocking it. The front-matter standards spec (design-038) section 6.2
escalates this rule to `error` in enforcement phase C, at which point the
`identifier` field also becomes required on new files. Phase C starts when the
identifier minting service deploys, so a repository with mismatched shoulders
has until then to converge.
