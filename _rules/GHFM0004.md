## Trigger

An unquoted YAML 1.1 boolean token appears in a value position inside the front
matter. The tokens are `yes`, `no`, `on`, `off`, `True` and `False`, in any
case. The scan runs before the parse, so it sees the text as written rather
than whatever the parser has already coerced it into.

## Why the rule exists

YAML 1.1 coerces those six tokens to booleans. YAML 1.2 does not. The harness
targets 1.2, but the parsers in the toolchain still apply the 1.1 heuristic in
places, so the same document reads differently depending on which engine loads
it. A field holding the two-letter country code `NO` becomes `false`, a
`review-cycle: on` becomes `true`, and nothing in either document announces the
change. This is the classic Norway problem, and quoting is the entire fix.

## Fix

1. Wrap the value in quotes: `description: "yes"` rather than
   `description: yes`. Single or double quotes both work; the harness has no
   preference.
2. If the value is genuinely a boolean, write it as `true` or `false`
   lowercase, which is unambiguous in both YAML versions.
3. Do not rename the key to dodge the rule. The hazard is in the value, and it
   travels with the value.

**Quotable fix.** Paste this into a review comment:

> **GHFM0004 (yaml-1-1-hazard).** This value is one of the YAML 1.1 boolean
> tokens (`yes`, `no`, `on`, `off`, `True`, `False`) and is unquoted, so it
> reads as a string under one parser and a boolean under another. Quote it:
> `"yes"`. If you meant a boolean, write lowercase `true` or `false`.

## Enforcement

Default severity is `error`, and it blocks a pull request from enforcement
phase A onward, per the front-matter standards spec (design-038) section 6.2.
