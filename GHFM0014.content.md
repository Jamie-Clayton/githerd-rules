## Trigger

An initiative briefing (`type: initiative`) breaks the intake gate in one of
these ways. Each breach is its own diagnostic:

- There is no `## Goal` section, or it is empty, a list, or longer than one
  sentence. Common abbreviations (`e.g.`, `i.e.`, `etc.`, `vs.`, `cf.`) and
  inline code do not count as sentence ends.
- There is no `## Open Questions` section. A heading that starts with "Open
  Questions", such as "Open Questions for Designer Hub", counts.
- The Open Questions section has no list items and does not read `None.`
- A top-level question does not open with `[blocking]`, `[non-blocking]` or
  `[answered]`. Bold grades such as `**[blocking]**` are accepted. Nested
  bullets are notes on a question and need no grade.
- The briefing is `lifecycle: approved` while a question is still
  `[blocking]`.

Headings and list items inside fenced code blocks are ignored, so a briefing
can quote the template.

The gate does not apply to briefings dated before 2026-10-04, or to briefings
whose `lifecycle` is `archived`, `superseded` or `rejected`.

## Why the rule exists

A briefing is the starting point Designer builds on. It only works if it keeps
what intake checked apart from what intake was told. When an unverified premise
appears in the Problem Statement as a fact, Designer builds on it and has to
correct it later. The lifecycle-policy shared-contract briefing (init-115)
ended with a "Designer Corrections" section for exactly this reason: three of
its intake claims did not survive the first measurement. Written as a blocking
question, the same premise gets checked before anyone builds on it.

The one-sentence Goal does the matching job at the top of the document. It is
the line the dashboard and a cold reader see first. If it needs two sentences,
the briefing holds two goals and the Scope should say so.

The gate is adapted from the five-section completion gate of the `intent.md`
convention (oh-my-claudecode's `intent` skill). The Explorer hub briefing
template carries the same checks under "Intake gate".

## Fix

1. Add `## Goal` directly under the H1. Write one sentence with no qualifiers:
   the thing that changes and who notices. Move anything longer into Vision or
   Scope.
2. Add `## Open Questions` after Constraints and Assumptions. If nothing is
   unsettled, write `None.`
3. Start every top-level question with a grade. Use `[blocking]` if the
   briefing cannot be approved without the answer, and `[non-blocking]` if it
   can. End the line with who can answer it.
4. When a question is settled, keep it and regrade it in place:
   `- [answered] <question> -- <answer, and where it is recorded>`.
5. Do not set `lifecycle: approved` while any question is `[blocking]`.
   Answer it, regrade it with a reason, or leave the briefing at `draft`.

**Quotable fix.** Paste this into a review comment:

> **GHFM0014 (initiative-intake-gate).** An initiative briefing needs a
> one-sentence `## Goal` and an `## Open Questions` section that reads `None.`
> or grades every top-level question `[blocking]`, `[non-blocking]` or
> `[answered]`. A claim intake did not check goes in Open Questions, not the
> Problem Statement, and the briefing stays `draft` while any question is
> blocking.

## Example (violating)

Copied verbatim from `tests/fixtures/front-matter/ghfm0014-triggering.md`, so
it is executable against the validator rather than merely illustrative. It
produces three diagnostics: no Goal section, one ungraded question, and an
approved briefing with a blocking question.

````markdown
---
type: initiative
id: init-ghfm0014-fail
date: 2026-10-04
lifecycle: approved
---

# Ungraded Intake -- Initiative Briefing

## Problem Statement

The shared register has drifted between the two repositories.

## Open Questions

- Has the shared vocabulary actually diverged?
- [blocking] Which repository owns the shared layer? -- operator

Three findings: no Goal section, one ungraded question, and a briefing marked
approved while a question is still blocking.
````

Each repository carries its own copy of the policy register, and nothing

## Open Questions

## Enforcement

Default severity is `warning`, so it surfaces as an annotation and does not
block a pull request. The registry records it as enforcement phase B, a
candidate for escalation once the gate has had a bake-in period. Promoting it
to an error is a governance decision recorded as an amendment, not a silent CI
change. This rule postdates the front-matter standards spec (design-038)
section 6.2 phase listing.
