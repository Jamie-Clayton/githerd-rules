## Trigger

The front matter parsed, and then failed validation against the JSON Schema the
validator dispatched for the document's location. The dispatch is by path, and
the first matching pattern wins:

| Path | Schema |
| ---- | ------ |
| `docs/initiatives/` | `front-matter-initiative.json` |
| `docs/architecture/ADRs/` | `front-matter-adr.json` |
| `docs/specs/` | `front-matter-spec.json` |
| `docs/plans/` and any `*/plans/` | `front-matter-plan.json` |
| `docs/uat/` | `front-matter-uat.json` |
| `docs/workitems/` | `front-matter-workitem.json` |
| `docs/comms/` and `docs/reports/` | `front-matter-report.json` |
| `docs/ideas/` | `front-matter-idea.json` |
| `docs/archive/` | `front-matter-archive.json` |
| anything else | `front-matter-base.json` |

The message names the schema file and the validator's JSON Pointer, so the
offending field is identifiable without guessing.

## Why the rule exists

The dispatch table is the whole point of putting a document in a folder. A
decision record in `docs/architecture/ADRs/` promises a decision date and a
lifecycle; a design spec promises a lifecycle; a plan promises a status. Those
promises are what let the graph build, the dashboard and the registers read a
document without special-casing it. A file that sits in a folder without
honouring the folder's contract is worse than one that sits outside it,
because it looks conformant from the directory listing.

## Fix

1. Read the JSON Pointer in the message. It is the path to the failing field:
   `/lifecycle` means the `lifecycle` key, `/metrics/value` means the `value`
   key inside `metrics`.
2. Open the named schema under `schemas/` and read the constraint for that
   field: `required`, `enum`, `type` or `pattern`.
3. Fix the value, not the schema. A schema change goes through the
   schema-change path in the front-matter standards spec (design-038) section
   7, not through the document that tripped over it.
4. If the document is genuinely of a different class than its folder implies,
   move the file rather than bending its front matter to fit.

Enum mismatches on `type`, `lifecycle` and `status` are deliberately reported
at `warning` rather than `error` while the pre-standard vocabulary is retired.
That downgrade is a migration accommodation with an end date, not a permanent
exemption.

**Quotable fix.** Paste this into a review comment:

> **GHFM0003 (schema-validation-error).** This document's front matter does
> not satisfy the schema its folder dispatches to. Read the JSON Pointer in
> the diagnostic, open the named schema under `schemas/`, and correct the
> field to match the declared `required`, `enum`, `type` or `pattern`. If the
> document is really a different class, move the file instead of loosening
> its metadata.

## Example (violating)

Copied verbatim from `tests/fixtures/front-matter/ghfm0003-triggering.md`, so
the example is executable against the validator.

````markdown
---
type: spec
id: spec-hm003-fail
date: 2026-04-20
---

# Missing lifecycle

When placed under docs/specs/ this file dispatches to front-matter-spec.json,
which requires lifecycle. GHFM0003 (schema-validation-error) must fire.
````

## Example (compliant)

Copied verbatim from `tests/fixtures/front-matter/ghfm0003-passing.md`.

````markdown
---
type: spec
id: spec-hm003-pass
date: 2026-04-20
lifecycle: draft
---

# Has lifecycle

When placed under docs/specs/ this file passes front-matter-spec.json validation.
````

## Enforcement

Default severity is `error`, and it blocks a pull request from enforcement
phase A onward, per the front-matter standards spec (design-038) section 6.2,
with the enum-vocabulary downgrade described above.

## Formerly

Formerly `HM003` (`SchemaValidationError`). That code is retired: the validator
emits the `GHFM` identifier only, and the retired code survives as a
`deprecatedIds` entry in the SARIF output so an archived CI log still resolves
to this page.
