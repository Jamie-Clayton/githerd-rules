## Trigger

A document's `subject` list holds a string with a declared prefix that does
not name an active concept of the
[Subject Vocabulary Standard](https://jamie-clayton.github.io/githerd-rules/subject-vocabulary/).
A prefix is declared when it is `ability:`, or one the repository's register
opts into (`theme:` and `component:` unless the register lists its own).

Each such subject is its own diagnostic, on the line it sits on:

- The concept does not exist: a misspelling such as `ability:tracability`, or
  a local concept nobody has added to the register.
- The concept is retired. The message names the concept that replaces it.
- The register replaces the core abilities, and the subject is a core
  ability. The message names the local concept that exact-matches it, if one
  does.

Subjects without a declared prefix, such as `lineage` or `topic:anything`,
are plain keywords and are never reported.

If the register `docs/registers/subject-vocabulary.json` is missing,
unreadable, or pins a version the repository has not vendored, the rule
reports that once per run, against the register, and checks no subjects.

## Why the rule exists

A prefix is an opt-in: it says "this is a concept, resolve it", and the
dashboard and cross-repository roll-ups group documents by what it resolves
to. A misspelt concept resolves to nothing, so the document quietly drops out
of its group while still looking classified. A plain keyword makes no such
promise, which is why the rule leaves keywords alone.

Resolution is delegated to the standard's reference resolver, vendored with
the version the register pins, so the rule and the standard cannot disagree.

## Fix

1. Correct the spelling. The core abilities are listed on the
   [core scheme page](https://jamie-clayton.github.io/githerd-rules/subject-vocabulary/scheme.html).
2. For a retired concept, write the replacement the message names.
3. For a concept the repository needs, add it to the register's `concepts`
   with a `definition` and a `broader` ability.
4. If the string was never meant to be a concept, drop the prefix.

**Quotable fix.** Paste this into a review comment:

> **GHFM0015 (unknown-subject-concept).** A subject with a declared prefix
> (`ability:`, `theme:`, `component:` or one the register adds) must name an
> active concept. Fix the spelling, use the replacement of a retired concept,
> add the concept to `docs/registers/subject-vocabulary.json`, or drop the
> prefix to keep it as a plain keyword.

## Example (violating)

Copied verbatim from `tests/fixtures/front-matter/ghfm0015-triggering.md`, so
it is executable against the validator rather than merely illustrative. It
produces two diagnostics, on lines 6 and 7.

````markdown
---
type: adr
id: adr-ghfm0015-fail
date: 2026-10-10
subject:
  - ability:tracability
  - theme:nowhere
  - lineage
---

# Misspelt Subjects

Two findings: ability:tracability is misspelt, and theme:nowhere uses a
declared prefix for a concept no register defines. The plain keyword lineage
is not reported.
````

## Example (compliant)

Copied verbatim from `tests/fixtures/front-matter/ghfm0015-passing.md`.

````markdown
---
type: adr
id: adr-ghfm0015-pass
date: 2026-10-10
subject:
  - ability:traceability
  - ability:governability
  - lineage
---

# Resolved Subjects

Both prefixed subjects name core abilities, and the plain keyword lineage is
never checked.
````

## Enforcement

Default severity is `warning`, so it surfaces as an annotation and does not
block a pull request. The registry records it as enforcement phase B, a
candidate for escalation once the corpus carries prefixed subjects. Promoting
it to an error is a governance decision recorded as an amendment, not a
silent CI change. This rule postdates the front-matter standards spec
(design-038) section 6.2 phase listing.
